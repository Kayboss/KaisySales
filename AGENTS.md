# AGENTS.md — KaisySales

Project memory for AI coding agents. Read this before making any changes.

## Project Overview

KaisySales is a fintech/SaaS app for African (Ghanaian) entrepreneurs. Built with React + Vite on the frontend, Supabase (Postgres) on the backend, deployed on Vercel. GitHub repo: `Kayboss/KaisySales`.

Two mutually exclusive business modes (from `businessType` in settingsStore):
- **retail**: Inventory, Daily Sales, Expenses, Invoices, Reporting, Business Overview dashboard
- **services**: Income Tracking (one-time + recurring), Customers, Service Expenses, Service Invoices, Service Reporting

A user is either retail or services — never both. Components in each mode never overlap.

## Commands

- Lint: `npx eslint <file>` (must be **0 errors, 0 warnings**). The local rule `themeTokens/no-undefined-token` (in `eslint-rules/theme-tokens.js`) fails the build on any `theme.*` path absent from `themeTokens.js`; a missing token resolves to `undefined` and the style is silently dropped, which no other gate can see. Keys that `ThemeContext` adds at runtime must be listed in that rule's `RUNTIME_ALIASES`, and a test enforces they stay in sync.
- Build: `npm run build` (passes, ~1.2 MB bundle — chunk size warning is expected, not an error)
- Test: `npm test` (`node --test scripts/*.test.mjs` — unit tests for the fail-closed backend rules). Use the explicit glob; `node --test scripts/` also matches `test-authz.mjs` and will run the network suite by accident.
- **Deploy (IMPORTANT)**: `npm run release` — this is Gate 1 (lint → unit tests → prod-dep audit → secret scan → build → bundle scan), then the migration-ordering gate, and only deploys if every check passes. Never run a bare `vercel --prod --yes`; the GitHub webhook auto-deploy does NOT fire reliably, so deploys are always manual.
- **Push before deploying.** CI cannot see unpushed commits, so a deploy that skips `git push` ships code no gate has ever seen.
- Git: `git add -A`; `git commit -m "..."`; `git push origin master` (branch is `master`). Only commit when the user explicitly asks.

## Security gates

- `npm run verify` — Gate 1 body: `lint && test && audit && secrets && build && scan:dist`.
- `npm run audit` — `npm audit --omit=dev --audit-level=high`; production deps must be clean. `npm run audit:all` includes the build toolchain (informational).
- `npm run secrets` — zero-dependency scanner (`scripts/secret-scan.mjs`). Working-tree findings **fail**; `npm run secrets:history` additionally reports git-history findings as **advisory** (history is fixed by rotating credentials, not by a code change).
- `npm run scan:dist` — inspects the built bundle. Supabase **anon** JWTs are allowed (public by design; RLS is the only protection) and are decoded to confirm `role: anon`; a `service_role` JWT, PAT, or private key fails the deploy. It also asserts the configuration-error screen is present, so the fail-closed path cannot be deleted silently.
- `npm run test:authz` — the RLS suite (`scripts/test-authz.mjs`). See "Authorization tests" below. `npm run verify:full` = Gate 1 + authz.
- `.github/workflows/ci.yml` — Gate 2: on every push/PR it runs the Gate 1 steps, CodeQL SAST, and an OWASP ZAP baseline DAST scan, plus the `authz` job; on push it also asserts the live site still serves all six hardened headers. `.github/dependabot.yml` opens grouped dependency PRs weekly.
- `vercel.json` uses `rewrites` (not legacy `routes`). Legacy `routes` silently dropped the entire `headers` block, so CSP/HSTS/X-Frame-Options were never served. Keep the two in sync and re-check headers after any routing change.
- `npm run check:migrations` — the deploy-ordering gate (`scripts/check-migrations.mjs`). Runs inside `npm run release` between Gate 1 and `vercel --prod`. See "Deployment ordering" below.

## Deployment ordering

A frontend and its schema have to agree, and only ordering makes that true. Gate 1 cannot help: lint, audit, SAST, DAST and the build all look at the code, never at what production actually holds, so a screen reading a column the database has not gained yet ships as a silently broken screen.

- **Rule: expand → migrate → contract.** An additive migration (new table, new column, new policy) goes out **before** the frontend that uses it; a removal goes out **after** the frontend stops using it. Never ship both halves of a rename in one release.
- **The gate compares `supabase/migrations/*.sql` with `supabase_migrations.schema_migrations` on production** (one read-only Management API query) and blocks a deploy when a file on disk has never been applied there.
- **Drift only warns, never blocks**: the same migration applied under a different version stamp, or schema applied with no file here. Blocking would trap the release behind the very inconsistency it just found — fix the drift, do not let it stop a fix.
- **Fail closed.** No token, no project ref, a 401/403, a network error or an unexpected response shape all block the deploy: shipping without having checked the ordering is the failure the gate exists to prevent.
- **But a slow read is retried, not blocked.** The Management API answered the identical query in **1.0 s, 9.8 s and 52.8 s** on three consecutive runs, so a 15 s single attempt once blocked a release whose schema was in order — and surfaced as the bare string `fetch failed`. The gate now makes **4 attempts at 30 s each** with 1 s → 2 s → 4 s backoff, retrying only transport errors and `408/425/429/5xx`; a 401/403 still blocks on the first attempt, and a failure that survives the retries still blocks. The reported reason is the `error.cause` chain (`fetch failed <- TimeoutError: …`), because `fetch failed` on its own tells nobody anything. `READ_ATTEMPTS`/`READ_TIMEOUT_MS`/`describeFetchError` live in `scripts/migration-gate.mjs` and are pinned by `scripts/migration-gate.test.mjs`.
- **Needs `SUPABASE_ACCESS_TOKEN`** — the same personal access token that applies migrations through the Management API. Put it in the gitignored `.env`; never in Vercel, never committed (`.env` is excluded from the secret scan because it walks `git ls-files --exclude-standard`). `MIGRATION_GATE=skip npm run release` is the escape hatch, for when you know the pending migration is not what the frontend depends on.
- **Apply a migration via the Management API**, per "Supabase" below: `POST https://api.supabase.com/v1/projects/<ref>/database/query` with `Authorization: Bearer <PAT>` and `{ "query": "..." }`. There is no direct DB connection, so a file in `supabase/migrations/` means nothing until it has been applied by hand.
- Pure logic lives in `scripts/migration-gate.mjs` (node-tested); `scripts/check-migrations.mjs` is the CLI around it. To exercise the gate alone, `npm run check:migrations`.

## No localStorage fallback in production

- The localStorage fallback keeps a business's real records in one browser, unencrypted and unsynced. It is enabled **only** when `import.meta.env.DEV`.
- The rules live in `src/services/backendConfig.js` (import-free so they are unit testable). `src/services/supabase.js` calls `assertBackendAvailable()` in every auth and data method, and `App.jsx` renders `ConfigError` instead of mounting routes when the backend is missing. A production build with no credentials therefore fails loudly instead of accepting a sign-in and losing the data later.
- A missing `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` in production is a deploy error, not a demo mode. Check the Vercel environment variables before blaming the app.

### Signup and the mailer (fail loudly, never silently)

A user signed up, saw "nothing happens", clicked Create again, and was told to wait — three separate defects stacked on one screen. All three are fixed; do not reintroduce any of them.

- **Email confirmation must be OFF (`mailer_autoconfirm: true`).** The project has `smtp_host: null` and `rate_limit_email_sent: 2` — the built-in mailer can send **two** signup emails per hour for the whole project. With confirmation required, the third signup in any hour cannot finish, which is exactly what a marketing campaign produces. Turning the built-in mailer up is not an option: the limit is per project, not per user. If verification is ever wanted back, configure a real mailer first (Gmail app password on `smtp.gmail.com:587`, or Brevo/SendGrid single-sender), then flip `mailer_autoconfirm`, then confirm the accounts already waiting.
- **Both of those are dashboard-only settings.** The Management API PAT is **auth-config read-only**: `GET /config/auth` works, `PATCH` answers `403 Missing required permission(s): auth_config_write, project_admin_write` — unlike the read-only database token, no part of this is fixable from the CLI.
- **`site_url` must be `https://kaisy-sales.vercel.app/`, never a deployment URL.** The root of this deployment 308-redirects to `/landing/index.html`, a static page that never loads supabase-js — so a confirmation or recovery link that lands there is never consumed and the visitor stays logged out. `authService.signUp` and `resetPassword` therefore pass `emailRedirectTo`/`redirectTo` = `${window.location.origin}/login`, and `/login` is on `uri_allow_list` via `https://kaisy-sales.vercel.app/**`. **An auth link's target is part of the flow, not a detail.**
- **`signUp` returns `{ status, user }`, not a bare user.** GoTrue answers a repeat signup for an existing address with `{ user: null, error: null }` (older) or a user with an empty `identities` array (current). The old caller tested `if (result)`, so that reply produced neither success nor error — a dead button. The three statuses are `signed_in`, `needs_confirmation`, `already_registered`, and `src/utils/authMessages.js` turns them into words (pure, pinned by `scripts/auth-messages.test.mjs`).
- **`ensureFreeTrial` and `migrateLocalData` only run when `data.session` exists.** With confirmation on there is no JWT at signup, so every write is refused by RLS and rolled back. `ensureFreeTrial` is idempotent and already runs on every auth change (`authStore`), so a confirmed user still gets the free plan on first login.
- **GoTrue's throttle text was reaching users verbatim:** "For security purposes, you can only request this after 47 seconds". The old branch matched `/rate limit/i` only. All of its shapes (`over_email_send_rate_limit`, "too many requests", …) are now matched, the seconds are parsed, and the submit button disables for a real countdown.
- Accounts stranded while confirmation was on need `update auth.users set email_confirmed_at = now() where email_confirmed_at is null;` in the SQL editor; a `update` does not re-fire `handle_new_user`, so their `profiles` rows survive.

### Authorization tests (`npm run test:authz`)
- The anon key is public, so **database permissions are the only thing** protecting customer data. No linter, audit, SAST or DAST tool can prove that, so `scripts/test-authz.mjs` asks the live database over PostgREST exactly like an attacker would, using only the public anon key.
- It discovers tables and functions from `supabase/migrations/*.sql` and `src/**` (`.from('x')`, `UserRecords(…, 'x')`, `.rpc('x')`), so a table added in a future migration is covered automatically. The SQL is read with **comments stripped and `DROP TABLE` honoured**, so a name that appears only in prose or a table a later migration retired is not probed as if it existed — both once cost seven vacuous SKIPs. Column types are truncated at the first constraint word (`uuid primary key default gen_random_uuid` becomes `uuid`), because an untrimmed type matched no probe value, left the insert body empty, and PostgREST answered `PGRST204` (no such column) instead of a permission decision. `scripts/authz-discovery.test.mjs` pins all three, and `discover(root)` takes the tree it scans so the test does not depend on the cwd.
- Checks: **A** anon reads nothing, **B** anon inserts nothing, **F** anon executes no function (probed with 4 argument shapes), **C** user A cannot read user B's rows, **D** user A can read their own (liveness), **E** user A cannot update/delete user B's, **G** user A **can** update an audited column on their own row, **H** user A cannot read another business's rows on all nine tenant tables and an insert naming another `business_id` is rewritten to the caller's own, **I** a staff login reads its own branch (liveness), cannot read or write a sibling branch's `sales`/`branch_inventory`/`invoices`, cannot add a module to its own `business_members` row, and its expenses match whatever `reporting` says they should be.
- **H and I exist because C/D/E ask a person-scoped question.** A row can belong to a *business* with several logins; a staff login's rows carry the staff's own `user_id`, so "A cannot read B's rows" was never the tenancy question. Section I needs a **third, optional** account (`AUTHZ_STAFF_EMAIL` / `AUTHZ_STAFF_PASSWORD`) that is an active staff member of user A's business: a staff login cannot be simulated from an owner token, because every branch and module rule asks `my_membership()`. Without it, every I check reports SKIP — never PASS.
- **I builds its own probe rows as the owner** (a product, a `branch_inventory` row and a `sales` row at the sibling branch) and deletes them in a `finally`, so a refusal cannot be confused with "there was nothing there to see" and a broken cleanup is a FAIL, not litter. `AUTHZ_NO_WRITE=1` skips E, G and every write in H/I.
- A skip is reported as SKIP, never PASS. `subscription_plans` is the one intentional exception (public pricing catalogue) and the suite fails if it ever gains a `user_id`.
- **G exists because A/B/C/D/E/F could not see a real outage.** The audit triggers (`audit_profile_changes`, `audit_payment_changes`) were `SECURITY INVOKER` and called `log_admin_action`, whose ACL is `postgres` + `service_role` only — so every write by a signed-in user that touched an audited column died with `42501 permission denied for function log_admin_action` and rolled back, breaking `ensureFreeTrial`, `assignSubscription`, `cancelSubscription` and `confirmPayment`. A–F probe the **anon** key, which is refused either way, so the suite stayed green at 102 passed while the admin subscription screen was dead. **Any check that only ever uses the anon key cannot see a bug that only a signed-in user hits — G is the signed-in-user liveness probe.**
- **Do not "fix" that class of bug by granting EXECUTE.** `log_admin_action` is `SECURITY DEFINER`, so `GRANT EXECUTE ... TO authenticated` would let any user forge audit rows through `POST /rest/v1/rpc/log_admin_action`. Fix the *caller* instead: make the trigger function `SECURITY DEFINER` (owned by `postgres`, which already holds EXECUTE). `auth.uid()` reads the request's JWT claim, not the current role, so `actor_id` is still the real acting user and the trail stays honest. Migration `20261005153000`.
- The PostgREST schema endpoint is **service_role-only**, so the suite must never depend on it.
- The live database carries a **default ACL** (`pg_default_acl`) granting `EXECUTE` on every new function in `public` to `anon` and `authenticated`. `REVOKE ... FROM PUBLIC` is therefore **never sufficient** — name `anon, authenticated` explicitly, or the function stays callable with the public anon key. Migration `20261004010000` fixes this and sets `ALTER DEFAULT PRIVILEGES` for future functions.
- The **current** default ACL for new `public` functions is the inverse: `postgres` + `service_role` only, never `anon` or `authenticated` (`postgres=X/postgres,service_role=X/postgres`). That is fail-closed and correct, but it means a new function is **not** callable by a signed-in user until someone grants it. If app code needs to reach it, grant `EXECUTE` to `authenticated` deliberately — or route through a trigger as above. Check `has_function_privilege('authenticated', oid, 'EXECUTE')` before assuming a function is reachable from the client.
- `profiles.status` is `CHECK (status IN ('active','suspended'))`, so a probe value outside that set returns `23514`, not a permission error. Probe privileged columns with legal values or the result will mislead you.
- The authz suite probes each function with the **declared parameter names** parsed from the migration. This matters: PostgREST resolves a call by argument name and answers **404** to a name it does not recognise, so a probe that sends only `user_id` gets 404 for a function with any other parameter and would misreport it as "not exposed". `normalize_amount(text)` was reachable (HTTP 200) while the suite reported PASS. If you add a function with parameters, confirm the suite reports a real permission decision (42501), never a bare 404.
- Needs `SUPABASE_URL` + `SUPABASE_ANON_KEY` for A/B/F. C/D/E need two disposable test accounts; the write probe aims only at user B — **never point it at a customer's account.**
- The two disposable accounts are `authz-a-kbpff4u8xq@example.com` / `authz-b-kbpff4u8xq@example.com`. Passwords live in the gitignored `.env.authz`, and in CI as the `AUTHZ_USER_A_PASSWORD` / `AUTHZ_USER_B_PASSWORD` secrets. The suite signs in and resolves the UUIDs itself, so no ID variables are needed in CI. If a password is ever reset, **the matching GitHub secret must be reset too**, or C/D/E silently degrade to SKIP while the job stays green.
- CI reads the URL, anon key and both emails from repository **variables** (`gh variable`), but the two passwords from **secrets** (`gh secret`). The run on `0552b46` (2026-11-07) reported **183 passed, 0 failed, 24 skipped** and `discovered 27 table(s)`; seven of those skips were phantom tables and four were malformed insert bodies. To re-provision an account, run `update auth.users set encrypted_password = extensions.crypt('<pw>', extensions.gen_salt('bf'))` in the SQL editor. An `update` does not re-fire `handle_new_user`, so the existing profile row survives.

### Growth: acquisition & activation
- Two questions, one tab (**Admin → Growth**, `src/features/admin/AdminGrowth.jsx`): *which channel brings accounts that actually get used*, and *where do new accounts fall out*.
- **Attribution is write-once, in `public.acquisition`** (migration `20261102120000_acquisition.sql`), not a column on `profiles`. `profiles` is updatable by its owner, so a later settings save could overwrite — or forge — where the business came from. Here `authenticated` holds INSERT + SELECT on its own row and nothing else: there is **no UPDATE policy**, so the first touch is the only touch. `anon` is REVOKEd explicitly (a new table inherits the default ACL's full DML for `anon`).
- **Capture**: `rememberTouch()` (`src/utils/growth.js`) runs at app boot in `src/main.jsx` and writes the touch to `sessionStorage` (`kaisysales_acquisition`); `public/landing/js/main.js` does the same on the landing page before someone clicks through to `/login`. First touch of the session wins, so a later page cannot replace the channel that actually brought them. UTM (`utm_source|medium|campaign|content|term`) beats referrer, referrer host beats `direct`, and a referrer pointing at our own host is `direct`, never a fake "kaisy-sales" channel.
- **Flush**: `App.jsx` writes the stored touch once per signed-in account per page load (`acquisitionFlushedFor` module guard). `dbService.recordAcquisition` treats `23505` as success, so a repeat is a no-op rather than an error, and an unavailable table degrades to "not attributed" instead of breaking the app.
- **The funnel is four nested sets of people**, from data the admin screens already read: `Signed up` (all profiles) → `Signed in` (`last_sign_in_at`) → `First record` (any count in `fetchUsersWithStats`) → `Came back` (a **second day** in `page_visits`, 90 days; `fetchVisitDays`). A stage can never exceed the one before it, and `rate` is `null` (rendered "—") rather than 0 when the denominator is empty.
- **Coming back is a second day, not a second page view.** `page_visits` writes a row per route change, so counting rows would call someone a returning user on their first afternoon.
- Accounts with no `acquisition` row are shown as **Not attributed** and sorted last — never guessed at from another signal. `src/utils/growth.js` is pure (storage injected) and pinned by `scripts/growth.test.mjs` (17 tests).
- **Apply the migration before deploying the frontend**: without the table the funnel reads "Not attributed" and signup attribution is simply lost — no crash, but no data either. The deploy-ordering gate blocks it anyway (`disk N` vs `applied N-1`).

### Key tables
- `service_income`: id, user_id, client_name, amount, platform_fee, net_amount, platform_tag, milestone_label, payment_date, notes, **category** (TEXT, added by migration), created_at
- `recurring_income`: id, user_id, client_name, amount, frequency (monthly/quarterly/yearly), next_due_date, category (TEXT free text), active, timestamps
- `expenses`: id, user_id, title, amount (TEXT with a `GHS ` prefix — read it with `parseAmount()` from `src/utils/currency.js`, never `parseFloat` on the raw string), category, date, vendor, subcategory, renewal_date, is_asset, asset_lifetime_years, transaction_fee
- `categories`: id, user_id, name, type (income/expense/inventory/sales), created_at
- `profiles`: includes business_type, business_name, logo_url, avatar_color, currency
- `acquisition`: user_id (PK), source, medium, campaign, content, term, referrer, landing_page, created_at — write-once first touch (see "Growth" above)
- `assistant_parses`: id, user_id, input, kind (record/question/unknown), record_type (expense/sale/service_income), parsed (JSONB), saved, feedback (up/down), error, created_at, updated_at — telemetry for the retired extractor (see the Assistant section; it now has no writer).

### Tenancy: businesses, branches and staff

Retail only (services mode has no staff and keeps its own screens). Migrations `2026110312–15`.

- **Anchor tables**: `businesses`, `branches`, `business_members`, `business_invites`, `products`, `branch_inventory`. Every business table carries `business_id` (**NOT NULL** since M3); `sales`/`invoices`/`expenses` also carry `branch_id` (NOT NULL) and `sales.product_id`.
- **RLS is the only tenant scope.** `is_business_member()`, `is_business_owner()`, `has_module()`, `can_see_branch()`. `can_see_branch` also asserts the branch belongs to that business, so pairing your own `business_id` with another business's `branch_id` does not pass the owner side. Application code no longer filters by `user_id` — that would hide a shared business's rows.
- **`fill_tenant()` (BEFORE INSERT, 12 tables) rewrites `business_id`/`user_id` from `my_membership()`**, so a client cannot choose its tenant; an owner who leaves `branch_id` null is filed at the default branch, and a staff row is pinned to the staff's branch whatever it sent.
- **Only two modules exist: `sales` (always present) and `reporting`.** `reporting` unlocks Reporting, Expenses, the Overview totals and the assistant's money answers. `set_member_modules` is the database allow-list; `src/utils/tenancy.js` mirrors it and `scripts/tenant.test.mjs` fails on drift.
- **One active business per login** (unique partial index) and a staff row must name a branch (`staff_needs_branch`). `ensureBusiness` runs **only** from explicit onboarding — running it on every auth change would hand an invited cashier a business of their own.
- **Screens**: `App.jsx` derives nav and routes from `modules` (`canReport`) and shows the branch switcher only to an owner with more than one branch. `resolveActiveBranch`/`branchForWrites` in `utils/tenancy.js` decide what a screen reads and where a write lands (a staff branch is never taken from storage/localStorage). Team tab (`src/features/settings/TeamSettings.jsx`) is owner-only.
- **Sales and inventory writes go through the RPCs** (`record_sale`, `create_product`, `set_branch_stock`, `void_sale`): module, branch and stock are checked in one transaction, so the client no longer computes stock itself.
- **The assistant is mounted for every login**, but a staff login without `reporting` gets stock insights only and "aren't switched on" answers for money questions — RLS returns no expense rows, so answering normally would state `GHS 0.00` as fact.
- Per-branch *reporting* breakdown is not built yet: the branch switcher gives per-branch views; a consolidated "all branches" report is the sum, not a comparison table.
- **Deactivate, never delete.** `remove_member` never removed an `auth.users` row: it set `business_members.status = 'removed'`, so "Remove" promised a delete the database deliberately did not perform and left the person unreachable from Team settings. The button now says **Deactivate**, they are listed under **Deactivated** with a **Reactivate** action, and only an admin can delete a login permanently (`purge_user_account`). `reactivate_member(p_user_id, p_branch_id)` (migration `20261105160000`) is the owner-only inverse: it keeps their email, password and records, refuses an archived branch (a staff row must name a live branch), and reports a person who joined another business meanwhile as `This person is already active in another business` instead of a raw `23505` from `business_members_one_active`.

### Logins the owner creates (no email in the path)

Migration `20261105120000`, edge function `supabase/functions/create-staff`, screen `TeamSettings`.

- **The owner supplies email + temporary password**; nothing is sent (the project mailer can send two messages an hour). Only a service-role key can create an auth user, so it is an edge function, not an RPC: it verifies the caller's JWT with `getUser()` and requires an **active owner** membership, then creates the user with `email_confirm: true`, updates `owner_name`/`is_onboarded`, and inserts the `business_members` row (`role: staff`, branch, `modules`). Any failure after creation rolls the auth user back with `admin.auth.admin.deleteUser`, because a login with no membership would be shown the "create a business" wizard instead of their job.
- **The password is never stored** — it is returned once into the form's state so the owner can hand it over, and after that only GoTrue holds it. `src/utils/staffLogin.js` (`isEmail`, `passwordProblem`, `generateTemporaryPassword`) is the client copy of the policy the function enforces; `scripts/staff-login.test.mjs` pins both copies, because a deployed function cannot import from `src/`.
- **First sign-in must change it**, enforced by `user_metadata.must_change_password` (not a `profiles` column: it is set by the function and cleared by the same `auth.updateUser({ password, data: { must_change_password: false } })` call, so no extra write and no RLS exemption). `mapUser` exposes it, `CheckAuth` renders `SetPasswordScreen` until it is false. `authService.updatePassword` also notifies the listeners itself — if GoTrue's `USER_UPDATED` were ever missed the person would be stuck on a screen whose job they had already done.
- `create-staff` must be **deployed separately** (dashboard or CLI) and needs the `SERVICE_ROLE_KEY` secret, the same name `verify-admin` already uses. It is not covered by any gate: a broken function surfaces as an inline form error in Team settings, not as a failed deploy.

### Admin account lifecycle (suspend / deactivate / restore / purge)

Migration `20261105120000`, screens `src/features/admin/AdminUsers.jsx` and `AdminUserDetail.jsx`.

- **Two different "delete"s, deliberately.** *Suspend* (`set_user_status`) and *Deactivate* (`delete_user_account`, which sets `profiles.deleted_at`) are reversible and keep every record. *Delete permanently* (`purge_user_account`) removes the auth user, frees the email address and drops the business it owned. Deactivated accounts leave the working list and appear only under the **Deleted** filter, which is where Restore lives.
- **`ConfirmDialog` returns `null` when `isOpen` is falsy.** Both admin screens rendered it without the prop, so no dialog appeared and Suspend/Delete silently did nothing. Any new dialog must pass `isOpen` (these pass a literal `isOpen` inside an `&&`).
- **A hard delete was impossible until this migration:** `businesses.owner_id` is `ON DELETE RESTRICT`, and `log_user_action` inserted an audit row naming the actor during the cascade from `auth.users` → `23503`. Now `user_actions.user_id` is nullable with `ON DELETE SET NULL` (the history outlives the person; `actor` is NULL once the account is gone) and the trigger guards on `EXISTS (SELECT 1 FROM auth.users …)` rather than an exception block, to avoid a subtransaction on every write. `business_invites.used_by` is `ON DELETE CASCADE`, not SET NULL — a spent code must not look reusable.
- `purge_user_account` refuses the caller's own account, refuses an owner whose business still has active staff (remove or transfer them first), deletes owned businesses before the auth user, and is revoked from `anon`. Every other FK to `auth.users` is already `SET NULL`/`CASCADE`, so no further ordering is needed.

### Assistant (feature-flagged)

`VITE_ASSISTANT` in `src/utils/features.js` gates the whole thing (`ASSISTANT_ENABLED`, default on). The panel is a **reading surface, not an input method**: recording is left to the screens, which already do it well and validate what they are told, so a spoken sentence was a slower, blurrier way to fill the same form. The assistant instead does what no single screen can — it reads across every record and says what needs attention, then answers questions about the numbers. **All of it is computed on-device from the same stats the reports use; no model is in the loop and nothing leaves the device.** The `parse-record` Edge Function and Gemini are no longer called by the client (they remain deployed, unused).

- `src/utils/assistant/stats.js` — the only number source. `buildStatsByScope()` returns `statsByScope` keyed by `today / this week / this month / last month / this year / all time` (UTC ISO windows) by reusing the SAME pure helpers the dashboards use (`serviceProfit`, `buildOutstandingRows`, `summariseByCustomer`, `isOverdue`, inventory helpers), so the assistant can never disagree with a report. Sales only in retail; customers/outstanding/recurring only in services. `unpricedCount` (`countItemsMissingCost`) rides along so the insights list can flag a margin it cannot work out.
- `src/utils/assistant/engine.js` — `answer(question, context)` words those numbers deterministically (`classifyIntent` + scope regexes); import-light so it unit-tests in plain Node. Never recomputes a figure — it only formats what it was handed. **An intention to record is not a stats question**: `RECORDING_INTENT_RE` (from `recordingIntent.js`) gives `classifyIntent` a `recordGuide` intent for sentences like "I want to record an expenses", answered with the same walkthrough as `howto` instead of the empty-stats line "You haven't recorded any expenses this month yet". `HOWTO_TOPICS` carries a `modes` list — a services business has no Sales or Inventory screen, so its topics are filtered out and the income topic absorbs "record a sale" instead. `FINANCIAL_INTENTS` (expenses, profit, overview) are answered with `NO_FINANCIALS_TEXT` when the context says `canSeeFinancials: false`, and `help`/`suggestedQuestions` drop the money prompts for the same reason.
- `src/utils/assistant/insights.js` — the "needs attention" builder. Pure, import-light (only `formatCurrency`), node-tested (`scripts/assistant-insights.test.mjs`). `buildInsights({ mode, currency, role, modules, statsByScope, todayIso })` turns the SAME stats the engine consumes into a ranked list of `{ id, severity, title, body, route, action }`, sorted `high → medium → low → info`. `FINANCIAL_INSIGHTS` is dropped for a staff login without `reporting` (a "month running at a loss" needs expense rows RLS will not return); stock, overdue-balance and unpaid items stay. It never recomputes a figure and never compares incomparable windows: a month-to-date against a whole previous month would show a fall that has not happened, so that comparison is deliberately absent. A business with nothing recorded gets exactly one insight (where the first record goes) rather than a pile of empty ones.
- `src/utils/assistant/recordingIntent.js` — the single regex that recognises a statement of intent to record ("I want to log a sale"), kept separate so the intent can be tested on its own.
- `src/services/assistantContext.js` — loads every record in one `Promise.all` (api.js fetchers fail soft) and packages `{ mode, role, modules, canSeeFinancials, currency, businessName, statsByScope, projection }`. Insights and answers both come from this one context, so the panel cannot hold two different pictures of the business. `role` is `staff` only for a **retail** login whose membership says so; anything else (owner, services, membership not loaded yet — `businessRole` is null until `loadSettings` finishes) is treated as an owner, or the first paint would tell an owner their expenses are "not switched on".
- `src/store/assistantStore.js` — zustand: `open`, `initialQuestion`, `openAssistant(question?)`, `closeAssistant`, `clearInitial`.
- `src/components/assistant/AssistantPanel.jsx` — floating FAB + panel, mounted in `App.jsx` inside the signed-in `Layout` **for every login** (not just `canReport`): a cashier without `reporting` still has a branch to restock, so hiding the panel would hide the stock list too. What they do not get is a money figure — `buildInsights`/`suggestedQuestions`/`answer` receive `role`/`modules` and refuse expense and profit questions with "aren't switched on", because RLS returns no expense rows and the honest stats would otherwise state `GHS 0.00` as a fact. The landing view is the insights list (`InsightCard`, left border coloured by severity); tapping one navigates to the owning screen and closes the panel. Asking a question swaps the landing view for chat bubbles, with a chip back to the insights. A doorway question is auto-answered once context loads via the React-sanctioned setState-during-render pattern (not an effect — the lint rule `react-hooks/set-state-in-effect` forbids the naive version). Nothing is persisted; history resets on reload. **`Messages` carries `min-height: 0` and it is load-bearing**: without it the flex item's automatic minimum size makes the scroll area grow to fit a tall message instead of scrolling it, the panel (`overflow: hidden`) clips the excess, and on a phone the composer slides out of reach — the scroll "stops working". Every non-scroll sibling (`Header`, `Suggestions`, `Composer`) is `flex-shrink: 0` so only `Messages` yields.
- `src/components/assistant/AssistantDoorway.jsx` — renders `<Sparkles>…</Sparkles>` dashed button on empty states (Inventory, Daily Sales no-inventory, Sales History, Income Tracking, Customers) and opens the panel pre-primed with that screen's question. Returns `null` when `ASSISTANT_ENABLED` is off.
- Tests: `scripts/assistant.test.mjs` (engine), `scripts/assistant-stats.test.mjs` (stats), `scripts/assistant-insights.test.mjs` (insights) and `scripts/assistant-store.test.mjs` (store) run under the standard `npm test` glob. The store test pins down an anon-invisible bug class: `openAssistant` must reject non-strings (a React SyntheticEvent was once passed by the FAB's `onClick={openAssistant}` and rendered as a message child, tripping the global ErrorBoundary on every open).

#### Needs attention (deterministic, no model in the path)

Deciding what needs attention is a reading job, and it is the one thing the dashboards do not do: each screen shows its own records, none of them looks across all of them and says "this is what is wrong". The list is computed once when the panel opens, from `statsByScope`, ordered by severity, and every entry routes to the screen that fixes it.

- **What it says today**: overdue invoices and unpaid balances (services), out-of-stock and running-low items plus items with no cost price (retail), a month running at a loss, a month that has gone quiet, a recurring payment due within seven days (services). A business with nothing recorded gets one entry — where the first record goes — and nothing else.
- **Severity drives the order** (`high → medium → low → info`) and the `InsightCard` left border; `topSeverity(insights)` names the worst level present so a future badge can be driven from it without rendering the list.
- **It deliberately does not compare a partial window with a finished one.** "This month" ends today, so setting it against last month would report a fall that has not happened; that comparison is absent until it can be made honestly.
- **What replaced it**: the old "talk to open" path — `fastParse.js`, `openForms.js`, `recordHandoff.js` and the per-screen `consumeHandoff()` effects — was **deleted**. A spoken sentence had to match a known shape to beat the form, and the form already had the better error margin. The one piece kept is `IncomeTracking`'s **"Add Income" button** (`openAddIncome`), which closed a real gap: new income previously only ever arrived through a customer's "Mark Paid".
- `supabase/functions/parse-record/index.ts` **remains deployed but nothing references it.** It verifies the caller's JWT (`getUser`) and calls Gemini (`gemini-3.5-flash-lite`, override `GEMINI_MODEL`). Keep it byte-identical to what is deployed; `GEMINI_API_KEY` is still set (a function secret whose *name* is the contract — `npm run secrets` cannot verify it). No feature depends on the model being reachable, configured or unretired. If the client is ever pointed back at it, note the model string is the part that rots (`gemini-2.5-flash` was retired for new keys and answered `404`, which surfaces as a `502 model_error`), so read `function_logs` before touching the client.
- Table `assistant_parses` (migration `20261017132930`) now has **no writer** — `logParse` went with the record path. Policies remain (select/insert/update own via `user_id = auth.uid()`, admin SELECT via `is_admin()`, **no DELETE**); `anon` is revoked explicitly and `authenticated` holds SELECT/INSERT/UPDATE only. The column is `not null` with no default, so anything that inserts must set `user_id` itself. `scripts/test-authz.mjs` still auto-discovers the table from the migration, which is the point of leaving it in place.

## Gotchas

- **The Management API only runs DDL for a token that can write.** `POST /v1/projects/<ref>/database/query` answers `25006 cannot execute CREATE TABLE in a read-only transaction` when `SUPABASE_ACCESS_TOKEN` is a fine-grained token holding only read permissions: the request is executed as `supabase_read_only_user` (`default_transaction_read_only=on`), and `read_only: false` in the body does **not** override it. `POST /v1/projects/<ref>/database/migrations` answers `403 Missing required permission(s): database_migrations_write`. This is a token-scope problem, not a project problem: `GET /v1/projects/<ref>/readonly` still reports `enabled: false`, so sign-in and every app write through PostgREST keep working. Fix by creating a PAT with `database_write` (+ `database_migrations_write`) and putting it in `.env`, or by pasting the migration into the dashboard SQL editor.
- Vercel webhook auto-deploy unreliable → always `vercel --prod --yes` manually.
- Branch is `master`, not `main`.
- PowerShell environment (Windows): no `&&` chaining; use `;` or `if ($?) { }`.
- Windows CRLF warnings on git add are harmless.
- GitHub log/artifact APIs return **403** to this machine (no auth), so a red CI step must be diagnosable from its own step output. Print the evidence in the step, not just in an artifact.
- The DAST job must **not** use `docker run --network=host` for ZAP: it makes ZAP bind its own API port on the runner and the daemon dies with `Failed to start ZAP :(` (exit 3) before scanning anything. Use the default bridge plus `--add-host=host.docker.internal:host-gateway`, with the preview server bound to `0.0.0.0`, `--shm-size=2g`, and a writable workspace so the report lands in the volume.
- GitHub Actions cannot read repo `secrets.*` in an `if:` condition. The `authz` job tests for empty values in a shell step and gates the next step on an output instead.
- Expense `amount` is stored as TEXT with a `GHS ` prefix — always strip before parseFloat. Rows written before the 2026-09-30 currency switch still carry the old `GH₵` prefix; `parseAmount()` strips either, but **display must go through `formatCurrency()`/`formatCurrencyShort()`** so old and new rows render identically.
- Currency is displayed as the ISO code (`GHS`), never the `₵` glyph: `formatCurrency` uses `currencyDisplay: 'code'`. Tango Sans has no `₵` glyph, so the symbol was being drawn by Manrope inside Tango Sans figures.
- Recharts is the chart library (AreaChart, PieChart, BarChart) — do not hand-roll SVG charts.
- Income "Mark Paid" creates `service_income` + `sales` records; delete cascades.
- Lint must stay 0 errors / 0 warnings.
